# RCA — fe-archivio: Cloudflare "could not parse" origin error

## Problem statement
User could not open the production app; Cloudflare returned: "The origin web server sent a response that Cloudflare could not parse... empty response, malformed HTTP headers, or an otherwise invalid response." Reported right after a new deployment. History: an earlier prod deploy crashed at startup with a pymongo DuplicateKeyError building the unique index on `anagrafiche (company_vat, ruolo, chiave)`.

## What was verified (evidence)

### 1. Current deployment is live and healthy — NOT still rolling out
- Active run `61a72b67-3e60-497a-aeca-a0e88eb62f3f` (redeploy). `get_step_status`: every step success (wakeup, build, mongodb_migrate, manage_secrets, deploy, health_check) — health_check passed 2026-10-21 10:26:57.
- `preview_health_check /` → 200, real app HTML (title/bundle present), 595ms.
- `fetch_app_logs` (active run): `Started server process` → `Waiting for application startup.` → `Application startup complete.` → `Uvicorn running on http://0.0.0.0:8001`. Live `/api/*` calls returning 200 (users, anagrafiche, invoices, stats). No DuplicateKeyError, no index-build crash, no 5xx.

### 2. The DuplicateKey crash belongs to the EARLIER FAILED run — already fixed
- The pymongo DuplicateKeyError (`E11000 ... index company_vat_1_ruolo_1_chiave_1 dup key {company_vat:"01192570453", ruolo:"cliente", chiave:"01428910457"}`) is from run `2ae45a97-b92e-43ec-bec5-b7058b6afe7e` (failed, Oct 20, `K8sDeployNotRetryable` — backend died on startup, nginx shut down).
- The current code (startup `split_anagrafiche()` + `dedup_anagrafiche()` before `create_index`, and `create_index` wrapped in try/except OperationFailure) resolves it: the active run boots cleanly. No migration/index error on Atlas for the active run.

### 3. Root cause of the Cloudflare 520: a pod eviction + reschedule window (infra, transient)
`get_pod_events` (active run):
- 12:14:39 — old pod `...-7q922`: `Evicted pod: Underutilized`, then `Killing` (cluster autoscaler node consolidation of an underutilized node).
- 12:14:39 — new pod `...-z2zvl` scheduled; `Pulling image` 12:14:41; image pull took **35.0s**; `Container started` 12:15:16.
- 12:15:19 — `Unhealthy: Startup probe failed: HTTP probe failed with statuscode: 503` (one occurrence — nginx 503 while uvicorn not yet listening).
- Now: pod `z2zvl` `phase: Running`, container `ready: true`, `restart_count: 0`.

During the ~35–40s image-pull + startup window the k8s backend origin had no ready endpoint. This deployment uses a **Cloudflare frontend** (`frontend_type: cloudflare`): the worker proxies `/api` to the k8s backend. With the origin momentarily unavailable/not yet serving valid HTTP, Cloudflare surfaced it as the "could not parse / empty response" (520-class) error. This is the window the user hit; the app has since recovered.

### 4. Not implicated: csrf_guard / SameSite / CORS
No 403 responses and no 5xx in the active run logs; `/api/*` serving 200s and legitimate 401s (auth-gated routes). The backend `/health` 404 is benign (no FastAPI `/health` route; pipeline tolerates 4xx). None of these would produce a Cloudflare "could not parse" error — that signature is specifically an unavailable/invalid origin, which matches the eviction window.

## Root cause
Transient platform event: the backend pod was evicted for node consolidation ("Underutilized") and the replacement pod took ~35s to pull the image and boot (one transient 503 startup probe). During that window the Cloudflare worker had no valid backend origin to proxy `/api` to, producing the "origin returned an empty response / could not parse" error. The app recovered once the new pod became Ready. The DuplicateKey startup crash was the earlier failed run and is already fixed by the current code.

## Is a code fix needed?
No. The current image boots cleanly and the dedup + try/except fix resolved the index-build crash. No source change required for the Cloudflare error.

## Recommendations
- Reload the app — it is live again (verified 200 on `/` and `/api/*`).
- The eviction/reschedule brief unavailability is inherent to autoscaler node consolidation on the current setup; if brief outages during consolidation are unacceptable, raise with Emergent support to review pod disruption/consolidation behavior for this deployment.
